# RAG 어시스턴트 — 설명용 1페이지

MembershipFlow 사내 읽기 전용 어시스턴트. 면접에서 말로 설명할 때 쓰는 요약이다.
숫자는 조건을 붙여서만 말한다.

## 무엇을 만들었나

Slack 에서 "이용 가능한 구독 판정 기준이 뭐예요?" 같은 질문을 받아 저장소 코드와
문서를 근거로 답한다. **읽기 전용이다.** 쓰기 도구가 없고, 실행 요청은 거절한다.

## 흐름

```
질문
 → 분류   KNOWLEDGE / METRIC / CLARIFY / OUT_OF_SCOPE
 → 검색   (KNOWLEDGE) Elasticsearch BM25 + 벡터, RRF 융합
 → 답변   Gemini, 제공된 근거만 쓰도록 지시
 → 근거검증 인용 번호를 실제 근거와 대조
```

각 단계에서 말할 수 있는 것:

**분류** — 키워드 규칙(`rule_route`)이 먼저 명백한 건을 처리하고, 남은 건만
LLM 으로 보낸다. 모든 질문을 LLM 에 보내지 않아 지연과 비용이 줄지만, 대신
규칙이 잘못 가로채는 문제가 생긴다(아래).

**검색** — 키워드 검색과 임베딩 검색을 각각 돌리고 RRF 로 합친다. 코드 질문은
식별자가 그대로 나오는 경우가 많아 BM25 가 잘 듣고, 자연어 설명 질문은 벡터가
낫다. 한쪽만 쓰면 반대쪽 질문에서 후보가 안 나온다.

**근거검증** — 이게 핵심이다. LLM 에게 `[1] [2]` 로 근거를 달라고 시켜놓고
그대로 믿으면, 주지도 않은 3번을 인용하거나 "답할 수 없습니다"라고 하면서도
성공으로 집계된다. `verify_citations` 가 ① 없는 번호 인용 ② 거절 문구 ③ 인용
없음 세 가지를 잡아 `grounded=false` 와 실패 사유를 남긴다.
**`grounded=true` 는 "인용 형식이 맞다"는 뜻이지 "사실이 맞다"는 뜻이 아니다.**

## 관측한 실패 1건과 수정 근거

**증상.** `"환불 처리 방식은 어떻게 구현되어 있어?"` 가 거절됐다. 코드를 찾아
답할 설명 질문인데 실행 요청으로 분류됐다.

**원인.** `rule_route` 가 `_OUT_OF_SCOPE_HINTS` 의 `"환불"` 을 부분 문자열로 찾는다.
"환불해줘"(실행)와 "환불 처리 방식"(설명)이 같은 규칙에 걸린다. 같은 결함이
`_METRIC_HINTS` 의 `"현재"` 에도 있다 — `"현재 코드에서 구독 만료를 어떻게 판단해?"`
가 지표 조회로 간다. 2026-09-22 비교 실행에서 12건 중 2건이 이 경우였다.

**수정 여부.** 아직 안 고쳤다. 외부 분류기(TypeSafe Jev)를 규칙보다 먼저 두면
두 건 다 풀리는 걸 확인했지만(재생 기준 9/12 → 11/12), 미검토 라벨 12건 위의
숫자라 채택 근거로 부족하다고 판단했다. 어댑터는 설정으로만 켜지게 만들고
**기본값은 꺼짐**으로 뒀다. 켜고 끄는 코드와 회귀 테스트까지가 지금 상태다.

이 판단이 요점이다. 고칠 수 있는 걸 발견했지만, 근거가 12건짜리 미검토 합성
라벨이라 "된다"고 말할 수 없어서 기본값을 바꾸지 않았다.

## 수치를 말할 때 붙이는 조건

| 수치 | 조건 |
|---|---|
| 검색 Recall@5 0.55 → 0.70 (리랭커) | 라벨 10건, reviewed=false. MRR 은 0.525 → 0.478 로 **떨어졌다**. 제품에 적용 안 함 |
| Jev 분류 12/12 일치 | 합성 12건, 미검토 라벨. confidence 임계값 적용 시 11/12. 그 11/12 도 Gemini 폴백이 없는 조건이고 분류 단계까지의 수치다. Gemini 대비 비교 아님 |
| Jev 평균 0.576초 | 로컬에서 1회, 네트워크 포함 |
| pytest 265건 통과 | 외부 네트워크 없는 범위 |

## 아직 검증 안 된 것

- Slack 실제 사용자 멘션 왕복 — 등록 핸들러 테스트만 함
- 검색 평가 라벨 검토 미완. ret-006 은 질문 범위가 아직 안 정해짐
- 기존 held-out 5건은 개발 중 노출돼 독립 평가로 못 씀. 새 평가셋 필요
- Jev vs Gemini 실측 비교

## AI 사용 범위

코드 상당 부분을 Claude/Codex 와 함께 작성했다. 내가 한 것은 설계 판단과
수용 여부 결정이다: 무엇을 만들지, 어떤 실패를 막을지(근거검증 도입,
기본값 off 유지), 어떤 수치를 근거로 인정하지 않을지. 위 "수정 여부" 문단의
판단이 그 예다. 코드 한 줄까지 직접 타이핑했다고는 말하지 않는다.
