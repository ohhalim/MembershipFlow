# 독립 평가셋 — 준비 자료 (2026-09-22)

아직 평가셋이 아니다. **문항을 만들지 않았다.** 사람이 문항을 확정할 때 쓸
판정 기준과 실행 명령만 정리한 것이다.

## 왜 기존 것을 못 쓰나

`cases.draft.jsonl` 의 15건은 split 이 `tuning` 10건, `held_out` 5건이다.
둘 다 최종 평가에 쓸 수 없고, 이유가 다르다.

| split | 건수 | 못 쓰는 이유 |
|---|---|---|
| `tuning` | 10 | 검색 설정을 고르는 데 직접 썼다. 애초에 최종 평가용이 아니다 |
| `held_out` | 5 | **개발 중에 노출됐다.** 아래 참고 |

`held_out` 5건의 구체적 한계.

- 개발 과정에서 이 5건의 질문과 정답을 보면서 코드를 고쳤다. 점수가 좋아도
  "본 적 없는 질문에서 잘한다" 는 근거가 되지 못한다
- 15건 전부 `reviewed: false` 다. 사람이 정답을 확인하지 않았다
- 3건(ret-011, ret-014, ret-015)은 `notes` 가 비어 있어, 무엇을 정답으로 보고
  무엇을 범위 밖으로 뒀는지 기록이 없다 (`LABEL-REVIEW.md` 2번)

한 번 본 문항은 다시 독립이 되지 않는다. 새로 만드는 수밖에 없다.

## 누가 문항을 만드나 — 이 구분을 지킬 것

AI 가 초안을 뽑을 수는 있다. 그러나 **AI 가 만든 문항을 독립 최종 평가라고
부르면 안 되고, 사람 검토를 거쳤다고 써도 안 된다.** 라벨의 `reviewed` 를
`true` 로 바꾸는 것은 "사람이 확인했다" 는 사실 주장이고, 라벨을 만든 쪽이
스스로 뒤집을 수 없다.

| 단계 | 누가 | 결과물에 쓸 수 있는 말 |
|---|---|---|
| 문항 초안 | AI 또는 사람 | "초안", `reviewed: false` |
| 정답 확인 | **사람만** | `reviewed: true` |
| 채점 실행 | 자동 | 측정값 |
| 해석 | 사람 | 결론 |

문항을 AI 가 뽑았다면 그 사실을 `notes` 에 남긴다.

## 사람이 한 문항을 판정하는 기준

한 문항당 아래 다섯을 모두 만족해야 `reviewed: true` 로 올릴 수 있다.
하나라도 아니면 문항을 고치거나 버린다.

1. **답이 저장소 안에 있다.** 코드나 문서를 읽으면 답할 수 있다. 실행 중인
   시스템의 현재 수치가 필요하면 검색 평가 문항이 아니다
2. **정답 청크가 실제로 색인에 있고 개수가 분명하다.** anchor 가 가리키는
   청크가 0개도 여러 개도 아니다
3. **그 청크 본문만으로 질문에 답할 수 있다.** 호출만 하고 정의가 다른 청크에
   있으면 그 청크도 `expected_sources` 에 넣거나 질문 범위를 줄인다
   (ret-006 이 이 경우다. `RET-006-EVIDENCE.md` 참고)
4. **범위 밖이 `notes` 에 적혀 있다.** 무엇을 정답으로 보지 않는지 쓴다.
   예: "상수 숫자는 어느 청크에도 없어 범위 밖"
5. **개발에 쓰지 않았다.** 이 문항을 보면서 검색 설정이나 코드를 고친 적이 없다.
   한 번이라도 봤으면 `held_out` 이 아니다

### 몇 건이 필요한가

정하지 않았다. 15건 규모로는 소수점 차이를 말할 수 없다는 것만 분명하다.
건수와 합격 기준은 **측정을 시작하기 전에** 정해야 한다. 돌려 보고 정하면
그 수치는 근거가 아니다.

## 다음 실행 명령

평가셋 파일이 준비된 뒤에 쓴다. 아래는 이미 있는 CLI 이고 새로 만들지 않았다.

### 1. 선행 조건 확인

현재 ES · Phoenix · Slack 모두 떠 있지 않다(2026-09-22 확인). 평가에는 ES 와
색인이 필요하다.

```bash
cd ai-assistant
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:9208   # 200 이어야 함
# alias 가 가리키는 실제 인덱스와 청크 수 (상태 조회 전용 CLI 는 없다)
curl -s http://localhost:9208/_cat/aliases/mf-ai-chunks?v
curl -s http://localhost:9208/mf-ai-chunks/_count
```

활성 alias 는 `mf-ai-chunks` → `mf-ai-chunks-64460aa92eba4887a09aa7011522857d`
(317 청크, 임베딩 `BAAI/bge-m3` commit `5617a9f6…` 고정)로 기록돼 있다.
**기록 시점 값이고 현재 상태 보증이 아니다.** 위 명령으로 다시 확인한다.

### 2. 문항 파일 형식 확인

새 파일을 만들 때 기존 스키마를 그대로 쓴다. `evals/schemas/` 에 있다.

```bash
ls evals/schemas/            # retrieval-case.schema.json 이 문항 스키마다
uv run membershipflow-ai eval --help
```

### 3. 채점

```bash
mkdir -p evals/results/<날짜>-<주제>
uv run membershipflow-ai eval evals/retrieval/<새 파일>.jsonl \
  --split held_out \
  --retriever keyword --retriever hybrid \
  --output evals/results/<날짜>-<주제>/raw.json
```

`cases` 는 위치 인자다. `--retriever` 는 반복해서 준다. `--split held_out` 은
명시해야 한다(기본값이 `tuning`).

`--allow-draft` 는 `reviewed: false` 인 라벨로 돌릴 때만 붙인다. **그렇게 나온
수치는 최종 평가가 아니다.** 결과 디렉터리는 매번 새로 만들고 기존 수치를
덮어쓰지 않는다.

### 4. 기록

`evals/results/<날짜>-<주제>/` 에 `manifest.json` 과 함께 남긴다. 무엇을
측정했고 무엇을 안 했는지, 라벨이 검토됐는지를 같이 적는다.

## 이번에 하지 않은 것

- 새 모델 실험, 임계값 조정, 리랭커 채택
- 서비스 기동
