# 평가셋 라벨 검토 자료 (2026-09-20)

`cases.draft.jsonl` 15건은 전부 `reviewed: false` 다. 이 값을 `true` 로 바꾸는 것은
"사람이 검토했다" 는 사실 주장이라 **라벨을 만든 쪽이 스스로 뒤집을 수 없다.**
이 문서는 승인이 아니라, 사람이 빠르게 판단하도록 근거를 모아 둔 것이다.

`reviewed` 를 바꾸는 것은 이 문서를 읽은 사람이 한다.

## 무엇을 확인했나

15건 전부에 대해 기계적으로 확인한 것.

- anchor 가 실제 색인에 존재하는가 (경로 suffix 규칙으로 일치하는가)
- 일치하는 청크가 **정확히 1개**인가 (모호하지 않은가)
- 청크 본문이 질문에 답하는가 (본문을 직접 읽고 대조)

결과: **15건 모두 anchor 가 색인에 정확히 1건씩 존재하고, 본문이 질문과 대응한다.**
즉 "가리키는 곳이 없거나 엉뚱한 곳을 가리키는" 라벨은 없다.

아래는 그래도 사람이 판단해야 하는 항목이다.

## 판단이 필요한 것 5가지

### 1. ret-006 — 근거가 하나 부족할 수 있다 (중요)

질문: `여러 소스의 가격 중 이상치를 찾을 때 기준 가격과 이탈 정도는 어떻게 계산해?`
라벨: `AnomalyDetectionService > evaluatePriceOutliers` 한 건

이 청크는 `median(...)` 을 **호출만** 한다.

```java
double median = median(prices.stream().map(SourcePrice::price).toList());
double deviation = (sp.price() - median) / median;
```

"기준 가격을 어떻게 계산하는가" 의 실제 답(정렬 후 중앙값, 짝수 개일 때 평균)은
같은 파일의 **별도 청크** `AnomalyDetectionService > median` (L125-133)에 있다.

선택지
- (a) `median` 을 두 번째 `expected_sources` 로 추가한다
- (b) 질문에서 "기준 가격" 계산을 빼고 이탈 정도만 묻는다
- (c) 현재대로 둔다 — "어떤 값을 기준으로 삼는가" 까지만 묻는 것으로 읽는다

ret-009 처럼 근거 2개인 문항이 이미 있으므로 (a) 가 형식상 불가능하지는 않다.

### 2. held_out 3건의 `notes` 가 비어 있다

| case | notes |
|---|---|
| ret-011 | 없음 |
| ret-014 | 없음 |
| ret-015 | 없음 |

나머지 12건은 "무엇을 정답으로 보고 무엇을 범위 밖으로 두는지" 가 적혀 있다.
이 3건은 그 판단 근거가 기록되지 않았다. 채점 결과를 나중에 해석할 때 근거가 없다.

### 3. ret-011 · ret-015 의 anchor 가 한 조각이다

| case | anchor | 문서 |
|---|---|---|
| ret-011 | `실행` | payment-load-test.md |
| ret-015 | `공통 에러 응답` | API.md |

anchor 는 경로의 **연속된 suffix** 로 일치한다. 한 조각짜리 anchor 는 다른 문서에
같은 제목의 절이 생기면 바로 모호해진다. 지금은 각각 1건만 일치하므로 **현재는
문제가 없다.** 다만 `ret-010` 처럼 `심사 전 차단 항목 > 홈페이지·구매 흐름` 두
조각으로 쓰는 편이 깨지지 않는다.

### 4. ret-001 — 래퍼 메서드를 정답에 넣을지

질문: `이용 가능한 구독의 판정 기준은?`
라벨: `Subscription > isActiveAt`

같은 클래스에 `isActive()` 가 있다 (L239-241).

```java
public boolean isActive() {
    return isActiveAt(LocalDateTime.now());
}
```

판정 **기준** 자체는 `isActiveAt` 에만 있고 `isActive` 는 현재 시각을 넣어 호출하는
래퍼다. 그래서 현재 라벨이 맞다고 본다. 다만 "이용 가능한지 판단하는 진입점" 으로
읽으면 `isActive` 도 후보가 되므로 한 번 확인받는 편이 낫다.

참고: 이 문항은 검색이 가장 어려운 문항이기도 하다. 정답 청크가 vector 85위라
후보에 들어오지 못하고, 대응책 3종(쿼터·깊이·재작성) 모두 상위 5에 올리지 못했다.
**라벨 문제는 아니다.**

### 5. ret-014 관련 — 색인된 문서에 개인 이메일이 들어 있다

`docs/DEPLOYMENT.md` L80 의 certbot 명령에 실제 이메일 주소가 있고, 그 줄이
ret-014 의 정답 청크 안에 있다. 즉 **어시스턴트가 답변에 그대로 인용할 수 있다.**

라벨 문제는 아니다. 다만 지금 Slack allowlist 가 비어 있어(= 제한 없음) 봇이
초대된 어느 채널에서든 답한다는 점과 겹친다. 둘 중 하나는 정하는 편이 좋다.

- 문서에서 이메일을 지우고 재색인, 또는
- allowlist 를 채워 응답 채널을 제한

## held_out 에 대한 별도 문제

`docs/operations/RAG-RESUME-2026-09-15.md` 에 held_out 5건이 **이미 개발 중
노출된 자료**라고 기록돼 있다. 라벨을 검토해 `reviewed: true` 로 바꾸더라도
그 사실이 사라지지는 않는다.

최종 품질 수치가 필요하면 **한 번도 보지 않은 문항으로 새 held_out 을 만드는
것**이 선행 조건이다. 라벨 검토와는 별개의 작업이다.

## 검토자가 할 일

1. 위 5개 항목에 대해 결정한다 (특히 1번은 라벨이 바뀔 수 있다)
2. 결정에 따라 `cases.draft.jsonl` 을 고친다
3. 각 문항의 `reviewed` 를 사람 판단으로 바꾼다
4. held_out 을 최종 수치에 쓸지, 새로 만들지 정한다
