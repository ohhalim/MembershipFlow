# 리랭커 동일 후보 깊이 재측정 (2026-09-20)

`CORRECTIONS.md` 2번은 2026-09-11 리랭커 비교를 철회하면서 이유를 적어 뒀다.
`+rerank` 계열만 후보 30, 나머지는 k(=10) 이라 재정렬 효과와 후보 깊이 효과가
분리되지 않았다. 그 항목의 마지막 줄이 **"미수행: 동일 후보 깊이 재측정"** 이다.
이 실행이 그 미수행 항목이다.

## 조건 (모드 간 차이는 모드 자체뿐)

- 후보 깊이 **모든 모드 candidates=20, k=5**. 이게 이 측정의 전부다
- 인덱스 `mf-ai-chunks-64460aa92eba4887a09aa7011522857d`, 문서 317건 검증
- 임베딩 BAAI/bge-m3 `5617a9f61b02…`
- 리랭커 BAAI/bge-reranker-v2-m3 `953dc6f6f85a…`
  (`CORRECTIONS.md` 5번이 남긴 `reranker_revision=None` 상태로는 어떤 가중치로
  쟀는지 기록에 남지 않는다. 이번엔 고정했다)
- tuning 10건, 라벨 변경 없음, `strict_path=True`, offline=1, ES read-only
- `cases_sha256` `875197103cfae873…`, `code_sha` `4acd23d7a18b`

**후보 풀 동일성 검증**: `vector+rerank` 가 본 후보 20개가 `vector` 의 후보 20개와
chunk_id 순서까지 같은지 확인하고 다르면 중단한다. hybrid 도 같다. 결과
`{'vector+rerank': True, 'hybrid+rerank': True}`. 그래서 top5 차이는 재정렬 말고 설명할 것이 없다.

## 결과

| mode | recall@5 | 후보20 상한 | MRR | 전근거 충족 | 초/질문 |
|---|---|---|---|---|---|
| keyword | 0.35 | 0.50 | 0.3250 | 0.30 | 0.014 |
| vector | 0.55 | 0.90 | 0.5250 | 0.50 | 0.138 |
| hybrid | 0.45 | 0.70 | 0.4200 | 0.40 | 0.055 |
| vector+rerank | 0.70 | 0.90 | 0.4783 | 0.70 | 3.051 |
| hybrid+rerank | 0.70 | 0.70 | 0.4733 | 0.70 | 2.783 |

"후보20 상한"은 그 모드가 후보 20 안에 정답을 얼마나 담았는지다. 리랭커는 후보를
재정렬만 하므로 이 값이 `+rerank` 의 recall@5 상한이다.

## 케이스별 이동

vector -> vector+rerank
- 진입: ret-008(후보 8위 -> 5위), ret-009 최초결제(9위 -> 5위)
- 상승: ret-009 정기결제 4위 -> 3위
- **하락: ret-005 1위 -> 4위** (top5 안이라 recall 손실은 없고 MRR 만 깎인다)
- 후보에 있었으나 못 건짐: ret-002(20위), ret-004(19위)

hybrid -> hybrid+rerank
- 진입: ret-005(9위 -> 5위), ret-008(14위 -> 5위), ret-009 최초결제(7위 -> 5위)
- 상승: ret-009 정기결제 5위 -> 3위

## 읽히는 것

- 동일 후보 깊이에서 리랭커는 recall@5 를 올렸다. vector 0.55 -> 0.70,
  hybrid 0.45 -> 0.70. 전근거 충족률도 0.50 -> 0.70, 0.40 -> 0.70
- **MRR 은 vector 에서 오히려 내려갔다** (0.525 -> 0.478). 원인은 ret-005 가
  1위에서 4위로 밀린 것이다. 그 한 건으로 MRR 이 0.075 깎이고, 008/009 진입분이
  이를 다 메우지 못한다. 더 많이 건지지만 첫 정답은 더 늦게 나온다
- hybrid+rerank 는 상한 0.70 에 정확히 도달했다. 후보 안의 정답을 전부 top5 로
  올렸다는 뜻이고, 더 올리려면 후보 구성을 바꿔야 한다
- vector+rerank 는 상한 0.90 중 0.70 까지다. 남은 0.20 은 ret-002(후보 20위),
  ret-004(후보 19위) 두 건이고 리랭커가 끌어올리지 못했다
- 비용은 약 22배다. vector 0.138 -> vector+rerank 3.051 초/질문 (모델 로드는
  측정 밖, 추론만)

## 이 측정이 말하지 않는 것

- **2026-09-11 의 철회된 서술을 복권하는 것이 아니다.** 그때와 코퍼스, 인덱스,
  임베딩 모델, 질문 집합이 모두 다르다. 비교 가능한 두 측정이 아니다
- 케이스 10건이고 라벨은 `reviewed=false` 초안이다. recall@5 0.15 차이는
  1.5건 분량이다. 채택 근거로 쓰기엔 표본이 작다
- tuning split 은 이미 튜닝 판단에 쓰인 자료다. 이 수치를 최종 품질로 보고할 수
  없다. held_out 은 실행하지 않았다
- ret-005 하락이 이 리랭커의 성질인지 이 한 질문의 우연인지 구분하지 않았다
- 후보 깊이를 20 이외로 바꿨을 때는 측정하지 않았다. 전체 깊이 진단
  (2026-09-20-vector-full-depth)에 따르면 vector 정답 순위는 ret-001 만 85위이고
  나머지는 20 이내라, 후보를 50 으로 늘려도 상한은 그대로 0.90 이다

## CORRECTIONS.md 반영 제안 (미적용)

2번 항목의 "미수행: 동일 후보 깊이 재측정" 은 이 실행으로 수행됐다. 다만
"해당 조건에서 vector 대비 개선이 확인되지 않았다 / 현재 미채택" 이라는 유지 판단은
recall@5 기준으로는 더 이상 그대로 두기 어렵다. 기록 파일 수정은 리뷰 대상이라
여기서는 제안만 하고 건드리지 않았다.

## 재실행에 필요한 것 (이 브랜치에는 아직 없다)

이 브랜치는 `develop` 에서 땄고 결과 디렉터리만 담는다. 스크립트를 실제로 돌리려면
아직 `develop` 에 들어가지 않은 두 가지가 필요하다.

- `evals/results/2026-09-19-pinned-model-build/manifest.json` — 인덱스와 모델 신원의
  출처. 별도 증거 PR 로 올라간다
- `cli._load_validated_manifest` / `cli.check_identity` / `store.index_identity` —
  전환 검증 헬퍼. PR #376 (issue #375)

측정 자체는 이 둘과 무관하다. 두 헬퍼는 "이 실행이 올바른 인덱스를 봤는지" 확인하는
용도고, 검색 품질 수치는 `retrieve_for_mode` 의 후보 깊이 처리와 인덱스 내용만으로
정해진다. 그 후보 깊이 통일은 이미 `develop` 에 있다.

스택 PR 을 만들지 않으려고 `develop` 기준으로 뒀다. 위 둘이 머지된 뒤 재실행하면
같은 수치가 나와야 한다.
