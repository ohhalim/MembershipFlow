# 평가 결과 정정 기록

커밋 이력은 수정하지 않는다(amend/rebase 금지). 잘못된 서술은 이 문서로 정정한다.

## 1. baseline 채점 무효 (수치 자체가 틀림)

- 대상: `2026-09-10-baseline-k10.json`, `2026-09-10-baseline-k10.html`,
  커밋 `1020b55` 본문의 표
- 사유: `symbol_path` 이전 색인에서 측정했다. 경로를 `"."` 으로 이어붙여 저장하고
  `"."` 으로 분해해 복원했기 때문에, 제목에 `"."` 이 있는 섹션의 경로가 손상됐다.
  검색에 성공한 근거가 채점에서 실패로 집계됐다.
- 영향: 표시된 Recall@10 / MRR 이 과소 집계다.
- 대체: `2026-09-11-after-path-fix-k10.json`
- 조치: 원본 수치는 보존하고 `invalidated` / `superseded_by` 필드와 HTML 공지를 추가했다.

## 2. 리랭커 인과 해석 철회 (수치는 유효, 해석이 교란)

- 대상: `2026-09-11-rerank-experiment.html`, 커밋 `3ebf494` 본문의 리랭커 표
- 사유: 후보 깊이가 retriever 마다 달랐다. `+rerank` 계열은 30,
  나머지는 `k`(=10) 였다. 재정렬 효과와 후보 깊이 효과가 분리되지 않는다.
- 철회하는 서술: "리랭커가 hybrid 를 vector 수준으로 되돌린다"
- 유지하는 판단: 해당 조건에서 vector 대비 개선이 확인되지 않았다.
- ~~미수행: 동일 후보 깊이 재측정~~ -> **2026-09-20 수행.** 아래 8번 참조.
- 채택 여부: 여전히 미채택. 제품 기본값은 바꾸지 않았다.

## 3. 잘못된 유의성 규칙 제거

- 철회하는 서술: "케이스 15건이므로 1건 = recall 0.0667, 그 이하 차이는 우열의 근거가 아니다"
- 사유: 케이스마다 정답 근거 수가 다르다. `ret-009` 는 근거 2개라
  하나만 맞히면 macro recall 변화가 `0.5/15 = 0.0333` 이다. 변화폭이 균일하지 않다.
  또한 이것은 통계적 유의성 기준이 아니다.
- 조치: 리포트 문구를 사실 기술로 교체했다. 유의성 검정은 수행하지 않는다.

## 4. held_out 독립성 상실

- 사유: 리랭커 채택 판단을 `held_out` 5건을 포함한 전체 15건으로 수행했다.
- 철회하는 서술: 기존 `held_out` 5건이 독립 최종 평가 자료라는 주장
- 현재 상태: 해당 5건은 노출된 개발 자료다. 최종 검증에 쓰려면 새 케이스가 필요하다.
- 조치: `eval` 기본 split 을 `tuning` 으로 바꿨다. `held_out` / `all` 은 명시 선택해야 실행된다.

## 5. 리랭커 revision 이 임베딩 revision 과 결합돼 있었음

- 사유: `CrossEncoderReranker` 에 `settings.embedding_revision` 을 넘기고 있었다.
  서로 다른 모델의 revision 을 한 값으로 묶으면 어떤 가중치로 측정했는지 기록이 어긋난다.
- 조치: `reranker_revision` 설정을 분리하고 결과에 `reranker_revision` 을 기록한다.
- 현재 설정값: `AI_RERANKER_REVISION` 미지정 -> `None`.

## 6. 평가는 경로 복원 실패를 무시하지 않는다

- 사유: 매핑에 `symbol_path` 가 있어도 문서 `_source` 에서 빠지면 `symbol` fallback 이
  비어있지 않은 손상 경로를 만든다. "경로가 비었는지"만 보는 검사로는 통과한다.
- 조치: 평가 경로는 `strict_path=True` 로 `_source.symbol_path` 의 존재와 배열 타입을
  후보 전체에 대해 검증하고, 위반 시 `CorruptedPathError` 로 중단한다.
  서비스 경로는 기존 fallback 을 유지한다.

## 2026-09-12 HTML 출력 제거

- Phoenix를 조회 화면으로 사용. 별도 HTML 생성기와 기존 HTML 2개 삭제
- 위 HTML 파일명은 과거 측정 정정 대상 기록으로 유지
- 평가 결과 원본: stdout JSON 또는 `eval --output <path.json>`
- JSON의 점수·후보·매칭 순위·실행 조건 보존
- 현재 eval 경로는 Phoenix 평가 데이터셋/실험 업로드와 연결되지 않음
- Phoenix의 서비스 trace와 오프라인 평가 결과는 현재 별개. HTML 제거가 자동 연동을 의미하지 않음

## 8. 동일 후보 깊이 리랭커 재측정 (2026-09-20, 2번의 미수행 항목)

2번이 남긴 "동일 후보 깊이 재측정" 을 수행했다. 코드는 이미
`retrieve_for_mode` 가 모든 모드에 같은 `candidates` 를 쓰도록 고쳐져 있었고,
측정만 남아 있었다.

- 조건: tuning 10건, candidates=20, k=5, 인덱스
  `mf-ai-chunks-64460aa92eba4887a09aa7011522857d`(317청크),
  bge-m3 `5617a9f6…`, 리랭커 bge-reranker-v2-m3 `953dc6f6…`
- `+rerank` 가 본 후보가 base 모드의 후보와 chunk_id 순서까지 같은지 검증했다

| mode | recall@5 | pool@20 | MRR |
|---|---|---|---|
| vector | 0.55 | 0.90 | 0.5250 |
| hybrid | 0.45 | 0.70 | 0.4200 |
| vector+rerank | 0.70 | 0.90 | 0.4783 |
| hybrid+rerank | 0.70 | 0.70 | 0.4733 |

- 2번의 "개선이 확인되지 않았다" 는 **그 조건에 한한 서술로 유지**한다.
  동일 깊이에서는 recall@5 와 전근거 충족률이 올랐다(vector 0.55 -> 0.70).
  다만 vector 의 MRR 은 내려갔다(0.525 -> 0.478). 두 지표가 반대 방향이다.
- 2026-09-11 측정과 직접 비교하지 않는다. 코퍼스·인덱스·모델·질문 집합이 모두 다르다.
- 근거: PR #381, `2026-09-20-rerank-equal-depth/`

### 대응책 세 가지는 recall@5 를 못 올렸다

ret-001(정답이 vector 85위)을 계기로 세 가지를 쟀고 전부 기존 최고
(`vector+rerank@20` = 0.70)를 넘지 못했다.

| 대응책 | 결과 | 근거 |
|---|---|---|
| source_type 쿼터 | pool recall@20 이 점수순 0.900 을 못 넘음 | PR #389 |
| 후보 깊이 50/100 | recall@5 0.70 -> 0.60 -> 0.50 로 악화 | PR #389 |
| LLM 질의 재작성 | pool@20 0.90 -> 1.00 이지만 recall@5 0.55 그대로 | PR #391 |

ret-001 은 후보 깊이 100(진입 85위)과 재작성(진입 18위) 양쪽에서 후보에
들어왔지만 리랭커가 top5 로 올리지 못했다. 후보에 넣는 문제가 아니다.

- 모든 수치는 tuning split, 라벨 `reviewed=false` 초안 기준이다.
  held_out 미실행. 채택·미채택 결정 근거로 쓸 수 없다.
