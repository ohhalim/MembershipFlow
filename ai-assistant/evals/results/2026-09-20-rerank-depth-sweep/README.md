# 리랭커 후보 깊이 sweep (2026-09-20)

## 왜 이걸 쟀나

앞선 관측 세 개가 이 실험을 가리켰다.

1. 전체 깊이 진단: ret-001 정답은 vector 85위. 후보 20 밖이라 리랭커가 못 본다
2. 동일 깊이 리랭커 재측정: 후보 20에서 recall@5 0.55 -> 0.70, 상한 0.90
3. ret-001 원인 진단: 정답이 java 청크 중 13위이고, 위 12개와 점수가
   0.4719 대 0.4751 로 거의 붙어 있다. bi-encoder 가 이 띠를 구분하지 못한다

띠 안에서 구분하는 것이 cross-encoder 가 하는 일이다. 후보 깊이만 늘리면
ret-001 이 사정권에 들어오니(@100 상한 1.00) 건질 수 있어야 한다 — 가 가설이었다.

## 조건

바꾼 변수는 **후보 깊이 하나**다. 인덱스 `mf-ai-chunks-64460aa92eba4887a09aa7011522857d`(317청크),
bge-m3 `5617a9f61b02…`,
리랭커 bge-reranker-v2-m3 `953dc6f6…`, k=5, tuning 10건, ES read-only,
라벨·alias 변경 없음. `code_sha` `2cd3bb4c4b28`.

## 결과 — 가설은 틀렸다

| mode@depth | recall@5 | pool 상한 | MRR | 전근거 | 초/질문 |
|---|---|---|---|---|---|
| `vector@20` | 0.55 | 0.90 | 0.5250 | 0.50 | 0.17 |
| `vector+rerank@20` | 0.70 | 0.90 | 0.4783 | 0.70 | 2.91 |
| `vector@50` | 0.55 | 0.90 | 0.5250 | 0.50 | 0.06 |
| `vector+rerank@50` | 0.60 | 0.90 | 0.4583 | 0.60 | 6.77 |
| `vector@100` | 0.55 | 1.00 | 0.5250 | 0.50 | 0.06 |
| `vector+rerank@100` | 0.50 | 1.00 | 0.4333 | 0.50 | 11.05 |

**후보를 늘릴수록 리랭커가 나빠진다.** 0.70 -> 0.60 -> 0.50.
depth 100 의 상한이 1.00 인데 결과는 0.50 으로, 리랭크 없는 vector(0.55)보다도 낮다.

## 무슨 일이 일어났나

정답의 후보 내 순위와 리랭크 후 top5 순위를 비교하면 분명하다.

| case | @20 후보 -> 최종 | @100 후보 -> 최종 |
|---|---|---|
| ret-001 | 후보 밖 | **85위 -> 실패** |
| ret-005 | 1위 -> 4위 | **1위 -> 실패** |
| ret-008 | 8위 -> 5위 | **8위 -> 실패** |
| ret-009 최초결제 | 9위 -> 5위 | 9위 -> 5위 |

두 가지가 동시에 보인다.

- ret-001 은 **후보에 넣어 줘도 리랭커가 못 건진다.** 볼 수 없어서가 아니었다
- depth 20 에서 성공하던 ret-005·ret-008 이 depth 100 에서 밀려났다.
  ret-005 는 bi-encoder 기준 1위였는데도 top5 에 남지 못했다

즉 후보를 80개 더 준 것이 도움이 아니라 방해였다. 늘어난 후보 중 그럴듯해
보이는 것들을 cross-encoder 가 정답 위로 올린다.

## 읽히는 것

- 리랭커의 후보 깊이는 공짜 레버가 아니다. 이 세트에서는 20 부근이 낫고,
  깊이를 늘리면 품질과 비용이 같이 나빠진다 (2.91 -> 11.05 초/질문, 약 3.8배)
- "상한이 올라가니 결과도 올라간다" 는 직관이 여기서는 성립하지 않는다
- **ret-001 은 시험한 어떤 깊이로도 회수되지 않는다.** 원인 진단에서 본
  평평한 점수 띠를 cross-encoder 도 가르지 못한다

## 같이 확인한 것 — source_type 쿼터도 답이 아니다

전체 깊이 랭킹으로 오프라인 계산했다. 후보 20을 java q개 + 문서 (20-q)개로
구성했을 때의 pool recall@20:

| java 쿼터 | 0 | 3~11 | 13~16 | 17~19 | 20 |
|---|---|---|---|---|---|
| pool recall@20 | 0.200 | 0.800 | 0.850 | 0.900 | 0.800 |

점수순 그대로인 현재 기준값이 **0.900** 이다. 쿼터를 어떻게 잡아도 이를 넘지
못한다. 17~19에서 0.900 으로 같아지지만 ret-001 을 얻고 ret-009 를 잃는 맞교환이라
개선이 아니다. ret-001 정답이 java 청크 중에서도 13위라 얕은 쿼터로는 닿지 않는다.

## 남은 것

이 두 가지(깊이, 쿼터)는 후보 **구성**만 바꾼다. ret-001 의 문제는 구성이 아니라
질의와 청크가 만드는 점수 띠 자체라서 둘 다 듣지 않는다.

원인 진단에서 유일하게 효과가 컸던 것은 **질문을 바꾸는 것**이었다
(한국어만 쓰되 일반 어휘를 피하면 85위 -> 10위). 질의 재작성은 아직 재지 않았다.
LLM 호출이 추가로 들어가므로 비용과 변동성을 함께 재야 한다.
