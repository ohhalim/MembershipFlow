# 질의 재작성 실험 (2026-09-20)

## 왜 이걸 쟀나

ret-001 원인 진단(#387)에서 효과가 있었던 레버는 **질문을 바꾸는 것** 하나였다.
같은 한국어로 일반 어휘를 피해 구체적으로 쓰면 정답이 85위에서 10위로 왔다.
후보 깊이와 source_type 쿼터는 둘 다 듣지 않았다(#389).

그 레버를 사람 손이 아니라 LLM 재작성으로 자동화해도 같은 효과가 나는지 본다.

## 조건

- 인덱스 `mf-ai-chunks-64460aa92eba4887a09aa7011522857d`(317청크), bge-m3 `5617a9f6…`
- 재작성 `gemini-3.5-flash`, temperature 0.0, 출처: rewrites.json (고정본)
- 리랭커 bge-reranker-v2-m3 `953dc6f6…`, k=5, candidates=20
- tuning 10건, 라벨 변경 없음, ES read-only, 제품 기본값 변경 없음
- `code_sha` `a7a799cb5d27`

`+rerank` 변형은 **같은 후보 풀**을 재정렬한 것이다. 후보가 같으므로 차이는
재정렬뿐이다.

## 결과

| variant | recall@5 | pool@20 | MRR | 전근거 |
|---|---|---|---|---|
| `original` | 0.55 | 0.90 | 0.5250 | 0.50 |
| `rewritten` | 0.55 | 1.00 | 0.5250 | 0.50 |
| `fused` | 0.55 | 0.90 | 0.5250 | 0.50 |
| `original+rerank` | 0.70 | 0.90 | 0.4783 | 0.70 |
| `rewritten+rerank` | 0.60 | 1.00 | 0.4833 | 0.60 |

## 읽히는 것

**재작성은 후보 누락을 실제로 고친다.** pool@20 이 0.90 에서 **1.00** 으로 올랐다.
ret-001 정답이 원문에서는 후보 밖(전체 85위)이었는데 재작성에서는 후보 18위로
들어온다. 지금까지 시험한 것 중 ret-001 을 후보에 넣은 유일한 방법이다.

**그런데 recall@5 는 그대로다** (0.55 -> 0.55). 후보에 들어오는 것과 상위 5에
들어가는 것은 다른 문제다.

**재작성 + 리랭커는 원문 + 리랭커보다 나쁘다** (0.60 vs 0.70). 상한이 1.00 으로
더 높은데도 그렇다. 케이스별로 보면 원인이 하나다.

| case | 원문+rerank | 재작성+rerank |
|---|---|---|
| ret-001 | 후보 밖 | pool 18 -> **top5 실패** |
| ret-008 | pool 8 -> top 5 | pool 12 -> **top5 실패** |
| ret-005 | pool 1 -> top 4 | pool 1 -> top 2 |

재작성이 ret-008 의 정답을 8위에서 12위로 밀어냈고, 리랭커가 12위는 못 끌어올렸다.
그 한 건이 0.70 -> 0.60 의 전부다.

## 세 실험을 합치면

ret-001 정답을 후보에 넣는 방법은 두 가지가 확인됐다.

- 후보 깊이 100 (#389): 후보 85위로 진입
- 질의 재작성 (이 문서): 후보 18위로 진입

**둘 다에서 리랭커가 top5 로 못 올렸다.** ret-001 은 후보에 넣는 문제가 아니라
bi-encoder 도 cross-encoder 도 이 질의·청크 쌍을 가려내지 못하는 문제다.

지금까지 시험한 조합 중 recall@5 가 가장 높은 것은 여전히 **원문 + 리랭커 @20 의
0.70** 이다. 세 가지 대응책(쿼터, 깊이, 재작성) 중 이를 넘은 것은 없다.

## 비용

재작성 LLM 호출이 질문당 **14.082초**다. 검색
자체(0.06초)보다 두 자릿수 크다. 품질 이득이 없는 상태에서 이 비용은 정당화되지
않는다.

## 실행 중 발견한 harness 오류

첫 실행은 `rewritten` pool@20 이 0.60 으로 나왔다. 틀린 값이었다.
`reply.content` 가 문자열이 아니라 블록 리스트였고, 그대로 `str()` 해서
thinking signature 의 base64 덩어리가 질의로 들어갔다. 즉 재작성 질의 자체가
쓰레기였다. `extract_text()` 로 `type == "text"` 블록만 꺼내도록 고치고 다시
돌린 값이 위 표다. **첫 실행 수치는 무효다.**

## 고정된 재작성

`rewrites.json` 에 LLM 출력을 그대로 고정했다. 검색 부분을 LLM 호출 없이
재현하기 위해서고, 무료 할당량이 하루 20건이라 반복 호출이 불가능하기도 하다.
재생성하려면 그 파일을 지우면 된다.
