## 2. 매핑 확인 (`ddl-auto: validate`)

이 레포에는 실제 DB로 JPA 매핑을 확인하는 테스트가 없다. 지금 테스트는 WebMvcTest와 단위 테스트뿐이다. 그래서 로컬에서 앱을 띄워 확인한다.

```bash
DB_PASSWORD=root docker compose -f docker-compose.yml -f docker-compose.local.yml up -d mysql
./gradlew bootRun
```

- 성공: Flyway 로그에 V24 적용(또는 "up to date")이 나오고, `Started MembershipFlowApplication`이 뜬다
- 실패: `Schema-validation: missing column` 또는 `wrong column type` → 엔티티와 V24가 다르다는 뜻이다. 에러 문장을 그대로 남긴다
- 주의: 로컬 DB에 V24가 기록된다. 나중에 V24를 고치면 로컬 DB 볼륨을 초기화해야 한다 (운영에는 영향 없음)
- 위 명령은 10/11에 실행해 보지 않았다. 안 되면 에러를 그대로 가져온다

## 결과 (10/12 12:00 기록)

- 1·2단계 완료: `Attendance`, `Coupon` 엔티티 작성. 빈 MySQL에서 `bootRun`으로 `validate` 통과 확인 (`captures/08-entity-validate.txt`)
- 3단계 Repository는 10/13로 넘긴다
- 계획과 달라진 점
  - `@UniqueConstraint`는 넣지 않았다. 테이블은 Flyway가 만들고 `validate`는 유니크 키를 검사하지 않아서 동작에 영향이 없고, 레포에서도 24개 유니크 키 중 4곳만 적었다. 중복 방지는 V24의 유니크 키가 맡는다
  - `day_no` 1~7 범위 검사는 생성자에 넣지 않았다. 값은 서비스 계산으로만 정해지므로 10/13 서비스 테스트로 확인한다
  - 매핑 확인은 기존 로컬 볼륨 대신 버리는 MySQL 컨테이너로 했다. 로컬 DB에 V24가 기록되지 않아서 V24를 아직 고칠 수 있다
- 질문 답
  1. (본인, 리뷰 중 정리) NULL 칼럼에 기본형 → null을 담을 수 없고 값이 없으면 0이 된다. 그래서 NOT NULL인 `day_no`, `discount_rate`는 `int`, NULL이 되는 `expires_at`, `used_at`은 객체 타입(`LocalDateTime`). 본인이 "0은 null이 아니다"를 짚어 NOT NULL로는 0을 못 막는다는 점도 확인했다
  2. (AI가 템플릿에서 정함 → 본인 수용) `attendance_id`는 유니크 키로 1:1 → `@OneToOne(fetch = LAZY)`
- 처음 고른 답과 바뀐 이유 (본인 선택 → 확인 후)
  - `attend_date`: `Date` → `int` → `LocalDate`. 숫자로 빼면 11/1 - 1이 20261100이 되어 "어제"를 못 찾는다
  - `expires_at`, `used_at`: `LocalDate` → `LocalDateTime`. 만료 경계를 시각으로 판정하고(`now.isBefore(expiresAt)`), 결제 기록 `billedAt`과 맞춰 보기 위해서다
