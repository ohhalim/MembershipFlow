## 설계 메모 (#461)

### 1. 장애 재현 계획

**목표**
Paddle이 느릴 때 결제 요청이 톰캣 스레드를 붙잡아 시세 조회까지 느려지는지 확인하고, 서킷브레이커 적용 전후를 같은 조건으로 비교합니다.

**Paddle 지연 흉내**
- `PADDLE_API_BASE_URL`을 로컬 WireMock 주소로 바꿉니다.
- `POST /transactions`는 20초 뒤에 거래 ID를 응답하게 합니다. 현재 read-timeout 15초보다 길게 잡아 결제 요청마다 15초 동안 스레드를 잡고 시간 초과로 끝나게 합니다.

**부하 조건 (k6, 두 시나리오 동시 실행)**
- 시세 조회: `GET /api/v1/courses/{courseId}/prices/latest`, 초당 20건, 로그인 없음
- 결제 거래 생성: `POST /api/v1/subscriptions/paddle/transactions`, 초당 2건, 60초
- 톰캣 최대 스레드를 기본 200에서 20으로 줄인 축소 환경에서 잽니다. 15초씩 잡히는 요청이 초당 2건이면 10초 안에 20개가 모두 찹니다.
- 숫자는 처음 값입니다. 한 번 시험 실행한 뒤 조정하고, 조정한 값은 전후 측정에 똑같이 씁니다.

**테스트 회원 제약 (코드로 확인)**
- 회원 한 명은 진행 중 결제 시도를 하나만 가질 수 있습니다. 실패한 시도는 30분 동안 PENDING으로 남고, 같은 회원의 다음 요청은 Paddle을 부르지 않고 바로 `PAYMENT_IN_PROGRESS`로 끝납니다.
- 그래서 Paddle 호출 1건마다 다른 회원이 필요합니다. 구독 중이 아닌 테스트 회원 150명과 각자의 액세스 토큰을 준비합니다. 토큰 파일은 기존 `k6/payment-test-users.example.json` 형식을 씁니다.
- 측정을 다시 할 때는 PENDING 시도를 지우거나 새 회원을 씁니다.

**재는 값**
- 시세 조회 응답 시간 p95와 실패율
- 결제 거래 생성 응답 시간 분포. 적용 후에는 서킷이 열린 뒤 실패 응답까지 걸리는 시간
- 톰캣 바쁜 스레드 수(`tomcat.threads.busy`). Spring Boot는 톰캣 MBean 등록이 기본으로 꺼져 있어 `server.tomcat.mbeanregistry.enabled=true`가 필요한지 먼저 확인합니다.
- 전체 p95만 보지 않고 초 단위 시계열도 남깁니다. 9번에 적은 대로 적용 후에도 서킷이 열리기 전 구간은 스레드가 찰 수 있어, 전체 p95만으로는 차이가 작게 보일 수 있습니다.

**조건 고정**
같은 PC, 같은 데이터, 같은 k6 스크립트, 같은 지연과 스레드 수로 적용 전후를 잽니다. 결과는 `docs/evidence/<날짜>-circuit-breaker/`에 before와 after로 남깁니다.

### 2. 해지 처리 방안

**선임 조건**
1. Paddle이 느릴 때 해지 요청이 톰캣 스레드를 묶지 않아야 합니다.
2. Paddle 장애 중에도 사용자가 해지를 못 하게 되면 안 됩니다.

**지금 구조 (코드로 확인)**
- `SubscriptionService.cancel`은 요청 스레드에서 Paddle 해지 API를 부르고 응답을 기다립니다. Paddle이 돌려준 해지 적용일을 받은 뒤에만 구독이 `CANCELLED`가 됩니다.
- 그래서 Paddle이 느리면 해지 요청마다 최대 15초 스레드를 잡고(조건 1 위반), Paddle 장애 중에는 해지가 실패합니다(조건 2 위반).

**안 1. 해지 요청을 DB에 먼저 저장하고 바로 응답**
- 해지 요청을 저장하고 "해지 접수"로 응답합니다. Paddle 호출은 스케줄러 작업이 나중에 합니다.
- 조건 1과 2를 모두 지킵니다.
- 가장 큰 위험은 작업이 다음 결제일까지 Paddle 해지에 성공하지 못하면 사용자는 해지를 눌렀는데 돈이 나가는 것입니다.

**안 2. 평소에는 바로 호출하고, 실패하거나 서킷이 열렸을 때만 저장**
- 정상일 때는 지금처럼 Paddle이 확정한 해지일을 바로 보여 줍니다.
- 해지에도 서킷을 걸면 열린 뒤에는 바로 저장으로 넘어가지만, 열리기 전까지는 해지 요청마다 최대 15초 스레드를 잡습니다. 조건 1을 일부 어깁니다.
- 실패한 요청을 다시 보내는 작업은 안 1과 똑같이 필요합니다. 결국 안 1의 장치를 모두 만들고 동기 경로를 하나 더 두는 셈입니다.

| | 안 1 | 안 2 |
|---|---|---|
| 조건 1 스레드 | 지킴 | 서킷이 열리기 전까지 어김 |
| 조건 2 장애 중 해지 | 지킴 | 지킴 |
| 정상일 때 화면 | 해지 접수, 확정은 잠시 뒤 | 바로 해지 확정 |
| 해지 완료 경로 | 하나 (스케줄러) | 둘 (요청 스레드, 스케줄러) |

**추천: 안 1**
- 선임 조건 두 개를 모두 지키는 안은 안 1뿐입니다.
- 해지는 다음 결제 주기부터 적용됩니다. Paddle 반영이 몇 분 늦어도 결제일 전에만 반영되면 사용자가 받는 결과는 같습니다. 정상일 때 바로 확정해 주는 안 2의 장점이 크지 않습니다.
- 해지가 완료되는 경로가 하나라 상태를 따라가기 쉽습니다.

**안 1을 만들 때 지킬 것 (구현은 별도 이슈, 이번 PR 1~3 범위 밖)**
- Paddle이 확정하기 전에는 구독을 `CANCELLED`로 바꾸지 않고, 해지 요청 기록을 따로 둡니다.
  - 미리 바꾸면 Paddle 반영이 실패했을 때 화면은 해지인데 결제는 나갑니다.
  - 그 사이 Paddle이 active 상태 웹훅을 보내면 `Subscription.syncPaddleActive`가 `cancelledAt`을 지웁니다.
- 실패하면 간격을 늘려 다시 보냅니다. 바로 다시 보내면 장애 중인 Paddle에 같은 요청만 쌓입니다.
- 다음 결제일 24시간 전까지 확정되지 않으면 ERROR 로그로 Discord 알림을 보내고 수동으로 처리합니다.
- `DELETE /api/v1/subscriptions/me` 응답이 해지 확정에서 해지 접수로 바뀌므로 프론트 변경이 필요합니다.
- 같은 구독에 해지를 두 번 보냈을 때 Paddle이 어떻게 응답하는지 샌드박스에서 확인합니다.

### 3. 서킷이 열렸을 때 응답

- 새 오류 코드 `PAYMENT_TEMPORARILY_UNAVAILABLE`을 추가합니다.
- HTTP 상태는 **503 Service Unavailable**로 합니다.
- 문구는 "결제 서비스 연결이 원활하지 않습니다. 잠시 후 다시 시도해 주세요."로 합니다.

**503을 고른 이유**
- 서킷이 열리면 Paddle을 부르지 않고 우리 서버가 일시적으로 거절합니다. "지금은 처리할 수 없고 나중에 다시 시도하면 된다"는 503의 뜻과 맞습니다.
- 레포 안에서도 같은 뜻으로 이미 503을 씁니다(`PAYMENT_WEBHOOK_RETRY_REQUIRED`).

**고르지 않은 것**
- 502 Bad Gateway: 상위 서버에서 잘못된 응답을 받았다는 뜻입니다. 서킷이 열리면 Paddle을 부르지 않아 받은 응답이 없습니다. 레포에서도 502는 외부 응답 확인 실패에 씁니다(`PAYMENT_STATUS_CHECK_FAILED`).
- 500 Internal Server Error: 우리 코드 오류로 읽히고, 다시 시도해도 된다는 신호가 없습니다.
- 지금의 402(`PAYMENT_FAILED`): 결제 수단 문제처럼 읽혀서 "잠시 후 다시 시도" 안내와 맞지 않습니다.

서킷이 닫힌 상태에서 Paddle이 5xx나 시간 초과로 실패하는 경우는 지금처럼 402를 유지합니다. 시간 초과는 결제 시도가 PENDING으로 남아 바로 다시 시도할 수 없기 때문에 #462에서 함께 다룹니다.

### 4. 서킷이 거절한 결제 시도 정리

**결정: 시도를 만든 뒤 서킷이 거절하면 그 시도를 실패로 바꿉니다.**
- 서킷이 거절했다는 것은 Paddle을 부르지 않았다는 뜻이라 거래가 중복될 위험이 없습니다.
- 처리는 기존 `failRejectedTransaction`과 같습니다. PENDING이고 거래 ID가 없는 시도만 FAILED로 바꿉니다.
- 그러면 사용자가 안내대로 다시 시도했을 때 `PAYMENT_IN_PROGRESS` 없이 다시 결제를 시도할 수 있습니다.

**고르지 않은 것: 서킷 상태를 먼저 보고 시도를 만들지 않기**
- 상태를 본 시점과 실제로 호출하는 시점 사이에 서킷이 열릴 수 있습니다. 그래서 결국 거절된 시도를 실패로 바꾸는 처리도 필요합니다. 처리 경로가 둘이 됩니다.
- 실패로 남긴 시도는 장애 중에 몇 명이 결제를 거절당했는지 세는 기록도 됩니다.

### 5. 라이브러리와 설정

**선택: Resilience4j (`resilience4j-spring-boot3`)**
- 실패와 따로 느린 호출 비율을 셀 수 있습니다. 이번 걱정은 Paddle이 실패하는 것보다 느려지는 것입니다.
- 어떤 예외를 실패로 셀지 고를 수 있습니다. 7번의 4xx 판정을 그대로 설정할 수 있습니다.
- Micrometer 지표를 내보내서 이미 열려 있는 `/actuator/prometheus`에 서킷 상태를 붙일 수 있습니다.
- 같은 라이브러리에 동시 호출 제한(Bulkhead)이 있습니다. 9번 안을 쓰게 되어도 의존성이 늘지 않습니다.

**고르지 않은 것**
- Spring Cloud Circuit Breaker: 구현체를 바꿔 끼울 수 있게 하는 추상화입니다. 구현체를 바꿀 계획이 없고, 레포에 없던 Spring Cloud 의존성 관리가 새로 들어옵니다. 느린 호출 같은 세부 설정은 결국 Resilience4j 설정을 씁니다.
- Hystrix: 2018년부터 유지보수 모드라 새로 도입하지 않습니다.
- 직접 구현: 상태 전환, 동시성, 지표를 모두 직접 검증해야 해서 이번 일정에 맞지 않습니다.

**적용 위치: `PaddlePaymentsClient.createTransaction` 안에서 코드로 감쌉니다**
- 지금 클라이언트는 5xx와 시간 초과를 모두 `BusinessException(PAYMENT_FAILED_ERROR)`로, 429를 포함한 4xx를 모두 `PaddleTransactionRejectedException`으로 바꿔서 던집니다. 메서드 바깥에 애너테이션을 붙이면 7번의 판정(429만 실패로 세기)을 할 수 없어서, 바꾸기 전의 RestClient 예외를 보는 위치에서 레지스트리로 받은 서킷으로 감쌉니다.
- 서킷이 거절하면 별도 예외를 던지고, `PaddleCheckoutService`가 그 예외를 받아 4번의 시도 정리와 3번의 503 응답을 합니다.

**처음 설정값 (PR 1 측정 후 조정)**
- 집계 방식은 최근 60초 시간 기준입니다. 결제 요청이 적어서 건수 기준으로 하면 몇 시간 전 결과가 계속 남습니다.
- 최소 호출 수는 5입니다. 기본값 100이면 지금 트래픽에서는 서킷이 열리지 않습니다. 반대로 60초 안에 결제가 5건도 안 되면 스레드가 찰 위험도 없으니 열리지 않아도 됩니다.
- 실패율과 느린 호출 비율은 각각 50%를 넘으면 엽니다.
- 느린 호출 기준은 처음에 5초로 둡니다. read-timeout 15초보다 길면 모든 호출이 15초에 끝나므로 기준이 의미가 없습니다. 샌드박스 정상 응답 시간을 PR 1에서 재고 정합니다.
- 열린 상태는 30초 유지하고, 반열림 상태에서 2건만 시험 호출합니다.

**상태 확인과 알림**
- 서킷 상태를 Prometheus 지표로 확인합니다.
- 서킷이 열릴 때 ERROR 로그를 한 번 남겨 기존 Discord 알림으로 받습니다. 열린 동안 거절되는 요청마다 ERROR를 남기면 알림이 쌓이므로 남기지 않습니다.

**인스턴스**
운영 백엔드는 컨테이너 하나입니다(nginx upstream 서버 하나). 서킷 상태는 인스턴스마다 따로 관리되는데, 지금은 하나라 문제가 없습니다. 늘리게 되면 인스턴스마다 따로 열리는 것으로 충분하다고 봅니다.

### 7. 추가 항목: Paddle 4xx를 서킷 실패로 셀지

**결정: 4xx는 실패로 세지 않습니다. 429만 실패로 셉니다.**
- 4xx는 Paddle이 정상으로 동작하면서 우리 요청을 거절한 것입니다. 잘못된 가격 ID나 요청 형식처럼 원인이 우리 쪽에 있습니다.
- 4xx를 실패로 세면 Paddle이 멀쩡한데도 서킷이 열려 모든 사용자의 결제가 막힙니다. 우리 쪽 문제 하나가 전체 장애가 됩니다.
- 429는 Paddle이 요청을 줄이라고 보내는 신호라 실패로 셉니다. 서킷이 열리면 요청이 줄어 Paddle 쪽 제한이 풀리는 데도 도움이 됩니다.
- 실패로 세는 것은 5xx, 429, 연결 실패와 시간 초과입니다.

### 8. 추가 항목: 요청 처리 중 부르는 외부 호출

요청 스레드에서 외부 응답을 기다리는 곳입니다(코드로 확인).

| 외부 호출 | 엔드포인트 | 타임아웃 | 이번 범위 |
|---|---|---|---|
| Paddle 거래 생성 | `POST /api/v1/subscriptions/paddle/transactions` | 연결 5초, 읽기 15초 | 포함 |
| Paddle 구독 해지 | `DELETE /api/v1/subscriptions/me` | 연결 5초, 읽기 15초 | 별도 이슈 (2번) |
| Toss 빌링키 발급, 결제 승인, 결제 조회 | `GET /api/v1/subscriptions/callback` | 연결 5초, 읽기 65초 | 밖 |
| Google OAuth 토큰 교환과 사용자 정보 조회 | `/login/oauth2/code/google` | 별도 설정 없음 | 밖 |
| 시세 사이트 수집 (Jsoup) | `POST /admin/collect` | 요청마다 15~20초 | 밖 |

- Toss 경로는 Paddle로 옮긴 뒤에도 코드와 엔드포인트가 남아 있습니다. 읽기 타임아웃이 65초라 Paddle보다 오래 스레드를 잡습니다. 실제 사용 여부를 확인한 뒤 정리할지 따로 정하는 것이 좋겠습니다.
- `POST /admin/collect`는 nginx가 `/admin/`을 막아 외부에서는 부를 수 없습니다.

요청 스레드 밖에서 부르는 것은 다음과 같습니다.
- 자정 정기결제 스케줄러의 Toss 승인
- 07:00 수집 스케줄러
- `/admin/collect/history`와 `/admin/collect/info`의 비동기 수집
- Discord 오류 알림(전용 스레드 하나)

### 9. 확인 요청: 서킷이 열리기 전 구간

서킷브레이커는 호출이 끝난 뒤에 결과를 셉니다. 그래서 Paddle이 응답하지 않으면, 첫 호출들이 15초 시간 초과로 끝날 때까지는 서킷이 열리지 않습니다.

1번 조건으로 예상하면 다음과 같습니다(PR 3에서 확인).
- 10초쯤: 결제 요청이 스레드 20개를 채웁니다.
- 17초쯤: 실패 5건이 쌓여 서킷이 열립니다.
- 30초 남짓: 열리기 전에 시작한 호출들이 시간 초과로 끝나면서 스레드가 풀립니다.

즉 서킷브레이커만 적용하면, 그동안 시세 조회는 여전히 스레드를 기다립니다. 장애 시간이 시작부터 끝까지에서 앞쪽 약 30초로 줄어드는 효과입니다.

이 구간까지 막으려면 Paddle 동시 호출 수를 제한하는 Bulkhead를 함께 둡니다. 제한을 넘는 요청은 Paddle을 부르지 않고 바로 거절하므로, 3번과 4번 처리를 그대로 쓸 수 있습니다. PR 2에 넣을지 판단 부탁드립니다.
