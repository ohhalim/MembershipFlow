# Paddle 거래 생성 지연 시 시세 조회 지연 재현, 서킷브레이커 적용 전 (#461)

## 조건
- 일시: 2026-11-27 14:1x~14:2x, 로컬 Apple M1 Max, 메모리 32GB
- 커밋: 3fe76ca. 애플리케이션 코드는 develop 2d5d62c와 같다
- 백엔드: JDK 21 `java -jar`, `loadtest/circuit-breaker/run-backend.sh`
  - 톰캣 최대 스레드 20 (`SERVER_TOMCAT_THREADS_MAX=20`)
  - 톰캣 MBean 등록 켬 (`SERVER_TOMCAT_MBEANREGISTRY_ENABLED=true`). 끄면 `tomcat_threads_*` 지표가 아예 나오지 않는 것을 확인했다
  - 관리 포트 8082 분리 (`MANAGEMENT_SERVER_PORT=8082`). 8081 스레드가 모두 차도 지표 수집 요청이 같은 줄에 서지 않게 하기 위함
  - IP당 분당 120건 제한 끔 (`APP_RATE_LIMIT_ENABLED=false`). k6 요청이 모두 같은 IP에서 나가므로 켜 두면 운영과 다르게 429로 막힌다
  - Paddle 주소를 WireMock으로 변경 (`PADDLE_API_BASE_URL=http://localhost:8089`). read-timeout은 기본값 15초 그대로
- Paddle 모의 서버: WireMock 3.13.1, `POST /transactions`를 20초 뒤에 거래 ID로 응답
- DB: MySQL 8.0 컨테이너(3307). 측정마다 `seed.py`가 테스트 회원 150명의 결제 시도를 지우고 시세 데이터를 다시 넣는다
- 부하: `k6/paddle-slow-upstream.js`, 두 시나리오 동시 실행
  - 시세 조회 `GET /api/v1/courses/900001/prices/latest`: 초당 20건, 0~100초, 로그인 없음
  - 결제 거래 생성 `POST /api/v1/subscriptions/paddle/transactions?planId=3`: 초당 2건, 10~70초, 요청마다 다른 회원
  - 요청 시간 제한 60초
- 바쁜 스레드: 8082에서 `tomcat_threads_busy_threads{name="http-nio-8081"}`를 1초마다 수집
- 3회 측정. 백엔드는 시험 실행 3회 뒤 재시작 없이 이어서 측정했다

### 로그
- 결제 거래 생성은 모두 `Paddle 거래 생성 실패` ERROR 로그와 함께 `PAYMENT_FAILED`(402)로 끝났다. read-timeout 15초로 끊긴 경우다
- 같은 회원이 다시 요청하면 Paddle을 부르지 않고 0.02초 만에 `PAYMENT_IN_PROGRESS`(409)로 끝나는 것을 측정 전 단건 요청으로 확인했다

## 해석
- 결제 거래 생성 요청이 나간 지 10초 만에 톰캣 스레드 20개가 모두 찼다. 설계 메모의 예상(초당 2건이 15초씩 잡으면 10초 안에 20개)과 같다
- 시세 조회는 실패하지 않았다. 대신 줄을 서서 기다리는 시간이 늘었다. 결제 요청 전 p95 40ms 안팎이 포화 구간에서 26초가 됐다
- 시세 지연은 10초마다 약 5초씩 늘었다. 결제 요청은 초당 2건이 15초씩, 즉 초마다 스레드 30개 분량을 요구하는데 스레드는 20개다. 처리량이 요구의 2/3에 그쳐 대기 시간이 초당 약 0.5초씩 쌓인다고 보면 관측값과 맞는다. 이 계산은 관측을 설명하는 모델이고, 톰캣 내부 큐를 직접 들여다본 결과는 아니다
- 결제 요청이 70초에 멈춘 뒤에도 쌓인 대기가 빠지는 데 약 33초가 더 걸렸다(바쁜 스레드 20개가 103초까지 유지)
- 결제 거래 생성 응답도 대기 시간이 더해져 p95가 41초였다. Paddle read-timeout 15초보다 훨씬 길다

## 한계
- 스레드를 200에서 20으로 줄인 축소 환경이다. 운영 수치로 옮기지 않는다. 운영에서 같은 현상이 나려면 스레드 수에 비례해 더 많은 결제 요청이 필요하다
- k6, 백엔드, MySQL, WireMock이 모두 같은 PC에서 돌았다
- Paddle 지연은 "늘 20초 뒤 응답" 한 가지 모양만 흉내 냈다. 5xx, 연결 실패, 간헐적 지연은 재지 않았다
- IP당 요청 제한을 끄고 쟀다. 운영에서는 사용자마다 IP가 달라 이 제한이 같은 방식으로 걸리지 않는다
- 운영의 nginx 시간 제한은 이 측정 경로에 없다
- 회당 k6가 보내지 못한 요청이 5건 있다(`dropped_iterations`). 전체 2,100여 건 대비 작아 결과 해석에는 영향이 없다고 본다

## 재현 방법
```
cd loadtest/circuit-breaker
docker compose up -d
cd ../.. && ./gradlew bootJar -x test
./loadtest/circuit-breaker/run-backend.sh
./loadtest/circuit-breaker/run.sh before-1
```
- 결과는 `build/loadtest/<이름>/`에 생긴다
- 시험 실행에서 바꾼 값: IP 요청 제한 끔(1차 실행에서 429 다수), 관리 포트 분리, VU 미리 할당 늘림(2차 실행에서 269건 누락), 요청 시간 제한 30초에서 60초, 시나리오 종료 대기 90초(3차 실행에서 21건 중단)
